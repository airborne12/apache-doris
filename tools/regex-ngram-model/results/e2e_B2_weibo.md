# B2 验收基准：weibo 500K 行 CJK 短文本（稀疏 gram）

> 本文件由 `tools/regex-ngram-model/e2e/bench_gram_regexp.sh` 实测生成，数字未做任何修饰。
> 结论先说：**体积达标（索引 = 原始列字节的 27.2 %，与 §4.7 对 CJK 码点 1-gram 的 26.2 % 预测吻合），
> 索引在行层面把 500K 行裁到 1–2 千候选（最好的一条 500,000 → 2），但可索引查询 p50 加速只有 1.22×
> （服务端口径 1.44×），未达到 §9.2 B2 的「p50 ≥ 10×」；结果集逐条一致（19/19）。**
> 直接原因：500K 行 / 65 MiB 的表在 192 核上无索引全扫只要 16–23 ms，比每查询固定开销还小，
> 比值没有可测空间。详见文末偏差分析。

## 2. 建表 DDL

tokenizer / analyzer 与 B1 共用 `gb_sparse`（`type=ngram, mode=sparse, min_gram=3, max_gram=16, density=0.25`）。
按 §6.1.1，非 ASCII 码点在稀疏模式下天然退化成「每个字一个 term」的 1-gram，无需为 CJK 单独配参数。

```sql
CREATE TABLE wb (
  id BIGINT,
  msg STRING,
  INDEX idx_msg_gram (msg) USING INVERTED PROPERTIES ("analyzer" = "gb_sparse")
) ENGINE=OLAP
DUPLICATE KEY(id)
DISTRIBUTED BY RANDOM BUCKETS 8
PROPERTIES ("replication_num"="1",
            "inverted_index_storage_format"="SNII",
            "disable_auto_compaction"="true");
```

## 8. 偏差分析

### D1（主因）：表太小，无索引全扫本身就在固定开销量级以内

500K 行 / 65 MiB 的列，在 192 核上被拆成 8 个 tablet 并行全扫，服务端耗时中位只有 **16–23 ms**；
而一次 `SELECT count(*)` 的固定开销（客户端连接 12 ms + FE 解析/规划 + fragment 建立/回收）
本身就有 11–20 ms。也就是说**「要省的那部分」和「省不掉的那部分」量级相同**，比值上限约 2×，
与索引质量无关。

取证（`德化窑`，全表只命中 1 行）：

| 模式 | 命中行 | 读列字节 / 页数 | 墙钟 |
|---|---:|---|---|
| 开索引 | 1 | **128 KB / 2 页** | 24 ms |
| 关索引 | 1 | 66.70 MB / 1,052 页 | 28 ms |

索引把列 I/O 降到 **1/520**、把 500,000 行裁到 **2 行候选**，端到端却只快 1.17×——
省下来的 66 MB 解压 + 50 万行正则在这台机器上只值 4 ms。

### D2：索引侧的行级效果与设计预期一致

18 条可索引查询中：

- `德化窑`、`太平公主.*审美`：500,000 → 1–2 候选（假阳性 0–1）；
- `三星.*手机`：243 真值 / 317 候选；`(三星|苹果|华为)手机`：233 / 528；
- `转发微博`：419 / 1,512；`手机微博`：30 / 2,344（放大 78×，因为 CJK 1-gram 下
  「手/机/微/博」四个字各自 df 很高，交集仍有噪声——这正是 §4.7 提到「CJK 加 τ 裁剪」的动机）；
- `http://t\.cn/[A-Za-z0-9]+`（29.2 % 宽泛）：145,870 真值 / 145,878 候选，几乎无假阳性。

`RowsGramIndexFiltered` 普遍在 49.7 万–50.0 万（占全表 99.4–100 %），说明**索引确实在裁**，
只是被裁掉的那部分本来也不贵。

### D3：如果要在本硬件上验证 B2 的 10×，需要放大语料

按 B1 的实测规律（同一套索引，30M 行时可索引 p50 = 3.23×，其中选择率 < 1 % 的子集服务端 p50 = 10.54×），
weibo 表要达到「无索引基线 ≫ 固定开销」的量级需要放大到千万行以上。
**本次严格按验收口径只跑了 500K 行全量语料，没有做人为放大，因此如实判 FAIL。**
需要注意：即使放大，B1 的经验表明 p50 仍然主要受选择率分布支配——
weibo 工作负载里 15/19 的选择率 < 1 %，这部分在足够大的表上有希望达到 10×，
而 `哈哈+`（4.06 %）、`http://t\.cn/…`（29.2 %）这类宽泛查询的上界仍是 ≈1/命中率。
